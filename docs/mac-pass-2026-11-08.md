## Setup

* **Tree:** steps 1 to 3 on master `dab89bcb` (the brief's commit). `node_modules` and the game folder were in place.
  `npm run build:wasm` rebuilt `script-vm.wasm`, which was stale; the two other kernels were current. Before steps 4 to 6,
  master was fast-forwarded to `dfd61024`. Its first new commit, `24ad3e65`, changes runtime code: it fixes two faults that held
  left levels alive (`base-epoch.mjs`, `script-window-host.mjs`, `sim-host.mjs`). Linux's 7.4.2 figures were measured with that
  fix. No Rust kernel changed, and `npm run build` made the production bundle for `--folder`.
* **Machine:** Apple M2 Pro (10 cores), 16 GB, macOS (Darwin 25.6.0), on AC power with the battery charged, Low Power Mode
  off, idle and display sleep held off for the session. The built-in display runs at **120 Hz** (ProMotion): every headed
  run's drawn-interval p50 is 8.3 ms. The Linux figures for 7.2.2 came from a 240 Hz display.
* **Browsers:** Playwright's Chromium 153.0.8010.12 (ANGLE Metal, "Apple M2 Pro") in worker mode, and Firefox 155.0 inline
  (its WebGL renderer string reads "Apple M1, or similar", Firefox's generic name for Apple GPUs). Viewport 1440×960 at
  DPR 1.
* **One browser job at a time**, no sub-agents. Only this session's own processes were stopped.
* **Audio muted.** `hitch-run.mjs` launches Chromium with `--mute-audio`, but sets no mute for Firefox, so every Firefox run
  had `"media.volume_scale":"0.0"` added to the brief's prefs:
  `--ff-prefs '{"privacy.reduceTimerPrecision":false,"media.volume_scale":"0.0"}'`. This scales the output to zero but leaves
  the audio graph running.
* **Host processes** (not this session's, left running; `ps` samples before each run in `roam/ps-*.txt` and
  `host-ps.log`): WindowServer 45 to 62% CPU; a Virtualization.framework VM 19 to 42% CPU with 0.7 to 1.7 GB resident;
  Messages 25 to 41%; coreaudiod about 15%; the Claude desktop app; the user's own Firefox. In the system log, a background
  Adobe process and OneMenu are the busiest writers (about 50 and 35 lines a second), and iCloud's `cloudd` syncs
  periodically. Spotlight indexing (`mds`, `mdworker_shared`) was active through the roams. Free memory was 34 to 50%
  (`memory_pressure`).
* **Saves corpus for 7.3.3:** not on the Mac. It was copied from the Linux host (`rsync`, read only there) to
  `.work/internet-saves/`. The 39 slots are in `.work/internet-saves/nicouzouf/files/Deus Ex`. The installed game's own `Save`
  folder, which the dev server also lists read-only, is empty, so no slot number collides.

rate, the page does about twice the frame work per second (rendering, uploads and their garbage). That may change how often
the collector runs. It is a difference between the two machines' runs, not a finding.

### What holds the left levels

Found after the pass, at the user's request (no runtime code changed). A scratch copy of `session-hour.mjs` (in `.work/held-levels/`,
outside Git) took a worker heap snapshot at the first reading where the worker held more than 5 live Wasm memories after the
forced collections. Run with the hour's defaults, it caught one at the Bar's first reading, 28.3 minutes in, right after the first
QuickSave and QuickLoad (6 memories, 977 MB; `held/full-held1-02_NYC_Bar_0-worker.heapsnapshot`, 487 MB). Two shorter variants
held nothing: Island, Training and Bar from a cold start, and the same three after a 1.5-minute warm-up of only those maps. The
hold is intermittent: in this run Training held nothing, where the hour's Training held one.

The snapshot has two `ScriptRuntime`s: the current level's (`host.scriptProcess.runtime`) and the left one's. The left one is the
**Bar's own previous instance**, the level the QuickLoad replaced: its `level.url.map` is `02_NYC_Bar`. The shortest strong paths
from the GC roots to it were traced over the snapshot's edges, with weak edges and WeakMap values left out (a WeakMap value lives
only while its key does). Two independent holders reach it. With both cut, the left runtime and its actors are unreachable, so in
this snapshot there is no third:

1. **The process-wide trace kernel's last model** (`trace-kernel.mjs`). `export let traceKernel` is one `TraceKernel` per realm.
   Its `base(model)` caches the model it last uploaded in `this.lastModel`. Its per-model ranges are in a WeakMap, but `lastModel`
   is a plain strong field. It only changes when that kernel is next asked about a different model, and a level's own traces go
   through its runtime's kernel (`createRuntimeTraceKernel`). So after a travel or a load, `lastModel` keeps the left level's
   `Level->Model`. Through it, the kernel keeps the `trackedLineNodes` closure that sim-host.mjs (line 203) defines on
   `level.model`. That closure's scope chain holds the left level's `runtime` and `level`, and with them its actors and arena.
   Path: module `trace-kernel.mjs` → `traceKernel` → `.lastModel` → `.trackedLineNodes` → its context → `level`, `runtime`.
2. **`setSpawnActorZone`'s getters in V8's allocation site** (`script-runtime.mjs` line 2840). Each call builds
   `const actor={isPawn}` and adds getters with `Object.defineProperties` (`deleted`, `position`, `region`, and for pawns
   `footRegion`, `headRegion`, `height`, `eyeHeight`, `playerReplicationInfo`). The getters are closures over the method's scope,
   which holds `this` (the runtime), `receiver` and `level`. `setSpawnActorZone` is a `ScriptRuntime.prototype` method, so its
   feedback vector is shared by every level's runtime. The literal's `AllocationSite` keeps an object whose map's descriptors hold
   the `AccessorPair` of the getters from the run that made it, and so that run's runtime and level. Path: the current runtime →
   `__proto__.setSpawnActorZone` → feedback vector → `AllocationSite` → `transition_info` → its map → descriptors → `AccessorPair`
   → `getter` → context → `this` (the left `ScriptRuntime`), `level`. This is the mechanism 24ad3e65 removed from the window host's
   `gcServices` getters (`defineReaders` in script-window-host.mjs). The site is replaced when V8 rebuilds that feedback, which
   would explain why the hold comes and goes.

Either holder pins at most one left level, which fits the 6 or 7 memories seen (one or two held levels). The release of both at
Battery Park and the step back to 5 at the end fit the trace kernel being asked about another model and V8 renewing the feedback.
Why the travel-only census holds nothing is not established. A likely reason is that each of its levels stands for 3 s: fewer
line checks reach the process-wide kernel, and fewer actors spawn through `setSpawnActorZone`, than in five minutes of play.

Not done: fixing either, which is a runtime change. Two fixes would follow the existing patterns. For the first, a level's dispose
(sim-host.mjs) could clear the process-wide kernel's `lastModel` and `lastBase`, as `forgetNoted()` does for the Base log. For the
second, `setSpawnActorZone`'s getters could be shared per name and read the object's own reader, as `defineReaders` does. Then
the hour and this probe would be rerun.
