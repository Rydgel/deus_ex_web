## Setup

* **Tree:** master `dab89bcb` (the brief's commit; origin/master has since moved to `dfd61024`, a docs-only change to row
  7.4.2). `node_modules` and the game folder were in place. `npm run build:wasm` rebuilt `script-vm.wasm`, which was stale;
  the two other kernels were current.
* **Machine:** Apple M2 Pro (10 cores), 16 GB, macOS (Darwin 25.6.0), on AC power with the battery charged, Low Power Mode
  off, idle and display sleep held off for the session. The built-in display runs at **120 Hz** (ProMotion): every headed
  run's drawn-interval p50 is 8.3 ms. The Linux figures for 7.2.2 came from a 240 Hz display.
* **Browsers:** Playwright's Chromium 153.0.8010.12 (ANGLE Metal, "Apple M2 Pro") in worker mode, and Firefox 155.0 inline
  (its WebGL renderer string reads "Apple M1, or similar", Firefox's generic name for Apple GPUs). Viewport 1440×960 at
  DPR 1.
* **One browser job at a time**, no sub-agents. Only this session's own processes were stopped.
* **Audio muted.** `hitch-run.mjs` launches Chromium with `--mute-audio`, but sets no mute for Firefox, so every Firefox run
  had `"media.volume_scale":"0.0"` added to the brief's prefs:
  `--ff-prefs '{"privacy.reduceTimerPrecision":false,"media.volume_scale":"0.0"}'`. This scales the output to zero but leaves
  the audio graph running.
* **Host processes** (not this session's, left running; `ps` samples before each run in `roam/ps-*.txt` and
  `host-ps.log`): WindowServer 45 to 62% CPU; a Virtualization.framework VM 19 to 42% CPU with 0.7 to 1.7 GB resident;
  Messages 25 to 41%; coreaudiod about 15%; the Claude desktop app; the user's own Firefox. In the system log, a background
  Adobe process and OneMenu are the busiest writers (about 50 and 35 lines a second), and iCloud's `cloudd` syncs
  periodically. Spotlight indexing (`mds`, `mdworker_shared`) was active through the roams. Free memory was 34 to 50%
  (`memory_pressure`).
* **Saves corpus for 7.3.3:** not on the Mac. It was copied from the Linux host (`rsync`, read only there) to
  `.work/internet-saves/`. The 39 slots are in `.work/internet-saves/nicouzouf/files/Deus Ex`. It has not been used yet.

**What explains roam 4, and what does not.** Its whole run is slower than the other three: page p50 8.6 ms against 6.9 to
7.3, and 104 fps against 112 to 114. The `ps` sample just before it shows the same resident set as before the other roams
(the VM at 21%). The hitch log's row times count from the dump's `meta.started`, so the long gaps fell at 12:30:31.08 (185 ms)
and 12:30:53.66 (167 ms) local time. In the system log (`/usr/bin/log show`, 40,000 lines from 12:30:05 to 12:32:00):
* **Spotlight** started two `mdworker_shared` processes at 12:30:28.07, 3 s before the 185 ms gap, and `mds` killed one of them
  at 12:30:51.76, 1.9 s before the 167 ms gap. Spotlight was equally busy through every roam, though: `mdworker` processes
  also started at 12:19:05 (the Chrome Island roam) and 12:24:54 (Firefox roam 1), and Spotlight wrote 13 to 84 log lines a
  minute from 12:19 to 12:32. It does not single out roam 4.
* An iCloud (`cloudd`) request completed at 12:30:52.64, one of about twenty in the two minutes.
* There is no memory-pressure, thermal, backup or install activity. The only `jetsam` lines are runningboardd's routine
  "not memory-managed" notices.

The dump has no Firefox GC events, since `--gclog` and `--profile` were not given. So the time between frames could be a
collector pause or the process being preempted, and only a Gecko profile could tell which. The host's background (Spotlight,
iCloud, the VM) was the same for all four roams, so it does not explain roam 4 by the evidence available. This is the brief's
stop condition.

**Firefox headless paces differently on the Mac.** It drew 104 to 114 fps here, against 57.7 to 59.1 fps for the same roams on
Linux. Row 7.2.4's Linux measurements (1.2 to 1.8 a minute) were taken under the slower pacing. At about twice the frame
rate, the page does about twice the frame work per second (rendering, uploads and their garbage). That may change how often
the collector runs. It is a difference between the two machines' runs, not a finding.

  the forced-GC readings, which leaves the heap clause unmeasured. That is a tool change, so it is left for the user to decide.
